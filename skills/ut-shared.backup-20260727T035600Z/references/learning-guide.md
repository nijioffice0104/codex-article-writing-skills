# UT・ユーザビリティ・UX基礎ガイド

このガイドは`ut-learning`の教材正本である。定義だけを読み上げず、利用者の身近な例と確認問題を組み合わせて使う。

## まず押さえる4つの概念

### UI（User Interface）

人が製品やサービスとやり取りする接点。画面、ボタン、入力欄、ナビゲーション、文章、音声操作などが含まれる。

UIは見た目だけではない。押せる場所、情報の並び、操作への反応、表示文言もUIである。

### UX（User Experience）

利用者が製品やサービスを知り、選び、使い、目的を達成し、その後にサポートを受けるまでを含む体験全体。使いやすさだけでなく、価値、信頼、感情、期待との一致も含む。

UIはUXを形づくる重要な接点だが、UXの全体ではない。配送が遅い、契約解除が分かりにくい、問い合わせ対応が悪いといった問題は、画面が美しくてもUXを損なう。

### ユーザビリティ（Usability）

特定の利用者が、特定の利用状況で、特定の目的をどれだけ有効に、効率よく、満足して達成できるかという性質。誰が、何を、どの状況で行うかを抜きに「使いやすい」とは判断できない。

この整理は[ISO 9241-11:2018](https://www.iso.org/standard/63500.html)の枠組みに基づく。

### ユーザーテスト（UT）

想定利用者またはそれに近い参加者に代表的なタスクを行ってもらい、その行動、迷い、発話、成功・失敗、回復のしかたを観察して、課題と改善機会を見つける方法。

参加者に製品の感想だけを尋ねるのではなく、実際に使う過程を観察する点が重要である。基本的な考え方は[Nielsen Norman GroupのUsability Testing 101](https://www.nngroup.com/articles/usability-testing-101/)も参照する。

## 4つの関係

```text
UX（体験全体）
└── UI（製品・サービスとの主な接点の一つ）
    └── ユーザビリティ（目的達成のしやすさを評価する観点）

UT（観察する方法）
└── UIや業務フローを実際に使ってもらい、
    ユーザビリティやUX上の問題を発見する
```

厳密には、ユーザビリティはUIだけでなく物理製品やサービス手順にも適用できる。上の図はデジタルプロダクトで理解しやすくするための簡略図である。

## 一つの例で比べる

ネットショップで商品を購入する場合:

- UI: 商品写真、検索欄、カートボタン、フォーム、エラー表示
- ユーザビリティ: 欲しい商品を見つけ、間違えず、過度な手間なく購入できるか
- UX: 商品を知った瞬間から、比較、購入、配送、開封、返品、サポートまでの体験
- UT: 参加者に「予算内で贈り物を選び、配送日時を指定してください」と依頼し、行動を観察する

## UTで分かること・分かりにくいこと

### 分かりやすいこと

- どこで迷い、止まり、誤操作するか
- 表示や用語をどう理解したか
- タスクを達成できるか
- どの回避策ややり直しを使うか
- 問題が利用体験へどう影響するか

### それだけでは分かりにくいこと

- 市場全体で何％の人に起こるか
- どのデザインが統計的に成果を上げるか
- 長期継続率や売上への正確な寄与
- 実装内部のコード品質

UTは課題の発見と理由の理解に強い。発生率や事業効果を確かめるには、アクセス解析、アンケート、A/Bテストなどを組み合わせる。

## 他の手法との使い分け

| 手法 | 主に答える問い | 主な証拠 |
|---|---|---|
| ユーザーテスト | 使う過程でどこに問題が起こり、なぜ起こるか | 行動、発話、成否、時間 |
| インタビュー | 利用者が何を経験し、どう認識しているか | 回想、意見、自己申告 |
| アクセス解析 | 実環境で何が、どの程度起きているか | イベント、遷移、離脱、件数 |
| A/Bテスト | どちらの案が特定指標をより動かすか | 無作為比較した定量結果 |
| アンケート | 集団の自己申告を同じ設問で比較できるか | 選択回答、尺度、自由記述 |
| QA・機能テスト | 仕様どおり動作するか、欠陥がないか | 期待結果と実結果 |
| 受入確認 | 利用・業務・契約上の受入条件を満たすか | 受入条件ごとのOK／NG |
| Unit Test | コードの小さな単位が想定どおり動くか | 自動テストの結果 |

同じセッションで受入確認とユーザビリティ観察を行うことはできるが、判定フィールドを分ける。機能が動いても使いにくいことがあり、使いやすそうでも重要な仕様を満たさないことがある。

## 良いUTタスクの作り方

悪い例:

> 右上の「新規登録」を押して顧客を追加してください。

操作方法と正解の表示名を教えているため、利用者が自力で見つけられるか分からない。

良い例:

> 新しく取引を始める顧客を、来週からチームで確認できる状態にしてください。

利用者の目的を示し、操作方法は教えていない。開始状態、成功条件、観察点はモデレータ側だけに持つ。

## ニュートラルなモデレーション

使いやすいプローブ:

- 「いま何を考えていますか」
- 「何が起こると思いましたか」
- 「普段なら次にどうしますか」
- 「その表示をどう理解しましたか」

避けるプローブ:

- 「このボタンを押せばよいと思いませんか」
- 「分かりやすいですよね」
- 「正解は右上です」

詰まった参加者を助ける必要がある場合は、助ける前の状態と時間を記録し、支援後の結果と分ける。

## 観察と解釈を分ける

| 種類 | 例 |
|---|---|
| 観察 | 参加者は検索結果を30秒見た後、前の画面へ戻った |
| 発話 | 「絞り込みがどこにあるか分からない」 |
| 解釈 | 絞り込み機能の発見可能性が低い可能性がある |
| 改善仮説 | 絞り込みの入口を検索結果上部へ移す |

解釈と改善仮説は、観察から追跡できるようにする。観察されていない原因を事実として書かない。

## よくある誤解

- UIが美しいからUXも良い: 見た目は一要素であり、価値、信頼、業務適合、サポートなどは別に確認が必要。
- 参加者へ感想を聞けばUTになる: 感想は有用だが、実際のタスク行動を観察しないと見えない問題がある。
- 1人で問題が出たから全員に起きる: 問題の存在を示す証拠にはなるが、母集団での頻度は分からない。
- 5人なら必ず十分: 目的、利用者の多様性、リスク、改善サイクルによって必要人数は変わる。
- UTはリリース直前に行う: 紙のラフ、試作、既存サービス、運用手順など、早い段階から実施できる。
- モデレータは困ったらすぐ助ける: 自力で回復できるかも重要な観察対象。安全や心理的負担に配慮しつつ、支援前を記録する。

## ミニ確認問題

1. 予約画面は分かりやすいが、予約後の確認メールが届かず不安になった。これは主にUI、ユーザビリティ、UXのどこまで関係するか。
2. 「参加者が保存ボタンを三回押した」と「反応が遅く感じたため不安だった」を、観察と解釈に分けるとどうなるか。
3. 新規利用者が料金プランを選べるか確かめたい。操作手順を教えず、どのようなタスクを提示するか。
4. 離脱率が20％である理由を知りたいとき、UTだけで十分か。何を組み合わせるか。
5. 機能は仕様どおり保存できたが、参加者は保存できたと気づかなかった。受入判定とユーザビリティ評価はどう分けるか。

### 回答の観点

1. メールは画面外も含む体験なのでUXの問題。確認状態の伝達というユーザビリティにも関係しうる。
2. 三回押したことは観察。不安だったという本人の発話があれば発話、発話がなければ解釈。
3. 利用者の状況、目的、制約を示し、ボタン名や手順を示さない。
4. UTで理由の仮説を深め、アクセス解析で発生箇所・規模を確認するなど、定性と定量を組み合わせる。
5. 保存処理が受入条件を満たせば機能はOKにできる。一方、状態の可視性にはユーザビリティ課題を記録する。
