# UT Scenario

最初に`../ut-shared/SKILL.md`を読み、対象プロジェクトの`ut.config.yaml`を読む。設定が無ければ`ut-setup`を先に使う。

## 入力

利用可能なものを優先順に集める。

1. UTの目的と対象ユーザー
2. 要件、受入条件、ユーザーストーリー、業務フロー
3. 画面設計、情報設計、プロトタイプ
4. 実装コード、差分、変更履歴、Issue／PR／チケット
5. 前回シナリオ、結果ログ、分析レポート
6. 利用者からの確認事項

情報源が無い場合は、利用者へ「何を確認すべきか」を聞く。追跡IDを創作しない。

## 初回作成

### 1. テスト目的と範囲を固定する

- 対象ユーザー
- 対象機能・ジャーニー
- 対象外
- 実施環境
- UTモード
- 外部影響やテストデータの有無

これらをモデレーター版の冒頭に記載する。

### 2. ユーザーの目的からタスクを作る

画面単位だけでなく、参加者が達成したい目的単位で分解する。例えば「登録画面を確認する」ではなく、「新しい案件を登録し、担当者が後から見つけられる状態にする」とする。

モードごとの設計:

- `usability`: 自然な文脈と目的を与え、理想操作を教えない。成功条件はモデレーター版だけに記載する。
- `acceptance`: 操作手順を再現可能な粒度にし、期待する表示・数値・状態変化を具体化する。
- `hybrid`: 参加者向けは自然なタスク、モデレーター向けは受入条件と観察点を併記する。

### 3. 実施順序を設計する

設定の`execution.order`を使い、原則として次の順に並べる。

1. データを変えないタスク
2. 元に戻せる変更タスク
3. 削除、公開、決済、通知など不可逆・外部影響タスク

後続タスクで件数や金額が変わる場合、前提となるbaselineと順序依存をモデレーター版に明記する。

### 4. シナリオIDを付ける

- セクションを`A`、`B`、`C`などの群に分ける。
- シナリオIDは`B-5`のように安定した形式にする。
- 要件ID、Issue、画面名など元情報を`source_id`として別に保持する。
- 既存番号を後から大きく振り直さない。

### 5. 2つのビューを作る

設定に従い、`../ut-shared/assets/`のテンプレートを使う。

#### participant view

- 文脈
- 達成したい目的
- 安全上必要な注意

正解操作、期待結果、評価観点、ヒューリスティック名、NG条件を載せない。

#### moderator view

- 開始状態
- 参加者へ伝えるタスク
- 成功条件・期待結果
- 観察点
- 必要時だけ使う中立的なプローブ
- 操作クラスと外部影響
- テストデータの命名
- 結果欄

### 6. テストデータを識別する

設定で有効な場合、データ名に`UT-<date>-<run-id>-`を使うよう記載する。シナリオ作成時にrun-idが未定ならプレースホルダーのままにし、実施開始時に確定する。

## 改訂

### 1. 既存版を読む

番号体系、セクション、対象外、保存場所、過去結果との対応を把握する。

### 2. 変更点を証拠から抽出する

設定された変更情報源を使う。GitHubが無ければGit差分、変更履歴、リリースノート、修正指示書などで代替する。

### 3. 差分を分類する

- 新機能 → 関連群の末尾または近接位置へ追加
- 期待結果変更 → 該当行だけ更新
- 対象外から実装済みへ → 対象外から本編へ移す
- 削除機能 → 行を黙って消さず、廃止理由と後継を改訂履歴へ残す
- 前回根本課題への対応 → 回帰確認シナリオを追加

新規IDは既存IDを壊さない。必要なら`D-2.1`のような補助番号を使う。

### 4. 改訂サマリーを付ける

追加、変更、廃止、未確認を冒頭にまとめる。新規行には`NEW`、変更行には`UPDATED`など視認できる印を付ける。

## シナリオ品質チェック

作成後に必ず確認する。

- 参加者向けビューに正解が漏れていない
- モデレーター版の全行に開始状態と成功条件がある
- 「正しく動くこと」のような曖昧な期待結果がない
- シナリオIDの重複がない
- 情報源へ追跡できる
- 変更タスクに実行固有のテストデータ規約がある
- 外部影響操作が識別され、確認ポイントがある
- HTMLタグと表構造が壊れていない
- 参加者版とモデレーター版のシナリオIDが一致する
- 対象外が明記されている

可能ならブラウザで両方を表示し、表の欠損、折り返し、狭い画面、印刷表示を確認する。

## 完了報告

- 作成・改訂した2つのファイル
- シナリオ件数と操作クラス別件数
- 変更点
- 外部影響操作とテストデータの有無
- 未確認事項
- 検証方法

## Hard NEVERs

- 参加者向けタスクに理想操作や期待結果を書く
- 要件IDを創作する
- 既存IDを理由なく振り直す
- 実装差分だけを見てユーザー目的を確認しない
- 本番の不可逆操作を通常シナリオとして無警告で入れる
- ユーザビリティ観察をOK／NGだけに縮約する
